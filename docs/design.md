# 設計

## 1. 設計方針

- Blender 内ロジックは Blender アドオンに閉じる
- Codex との接点は MCP サーバーに集約する
- 外部 AI サービス接続はアダプタ層で抽象化する
- 危険操作は必ずポリシーと承認を通す

## 2. 想定アーキテクチャ

```text
Codex
  -> MCP Server (Python)
      -> Transport Layer (HTTP local)
          <- Blender Add-on (long-lived local reverse connection)
              -> Blender Python API
      -> AI Provider Adapter
          -> OpenAI compatible API / other providers
```

## 3. コンポーネント

### 3.1 MCP Server

責務:

- Codex に公開するツール定義
- Blender 接続管理
- リクエスト検証
- 実行ジョブ管理
- AI プロバイダ呼び出し
- 監査ログ出力

候補実装:

- Python 3.11+
- 公式 MCP Python SDK v1.x
- `uv`

### 3.2 Blender Add-on

責務:

- Blender UI 提供
- MCP サーバーとの通信
- Blender API 実行ラッパー
- 結果整形
- 例外捕捉
- 常時接続状態の維持
- 再接続制御

候補実装:

- Blender Python API
- `bpy.types.Panel`, `bpy.types.Operator`, `bpy.app.timers`
- 多モジュール構成

### 3.3 AI Provider Adapter

責務:

- API キー設定管理
- モデル呼び出し
- 応答正規化
- リトライ/タイムアウト

## 4. 通信方式比較

### 採用案: ローカル HTTP + Blender 主導の常時接続

利点:

- 公式 MCP Python SDK と整合しやすい
- ローカル常駐アドオンとの相性がよい
- UI 側の接続状態管理と再接続制御を持たせやすい
- ログや検証がしやすい

欠点:

- Blender 側の接続維持責務が増える
- 単純な問い合わせより構成が少し重い

初期判断:

- MVP はローカル HTTP を採用する
- 接続の主導権は Blender アドオン側が持つ
- Blender アドオンは MCP サーバーへローカル接続し、常時接続または再接続制御を持つ
- WebSocket は現時点では採用しない

## 4.1 ローカル接続ポリシー

- MVP では接続先をローカルホストに限定する
- 想定バインド先は `127.0.0.1` または `localhost` とする
- 外部ネットワークインターフェースへの bind は既定で禁止する
- Blender アドオンから接続する相手先は明示設定されたローカルアドレスのみ許可する
- 将来的に外部公開を検討する場合も、別フェーズ Issue を起点に再設計する
- Blender 側の常時接続先もローカルホストに限定する

## 4.2 設定保持方針

- API キーはコードやリポジトリへ保存しない
- API キーは OS 環境変数またはローカル設定ファイル参照を前提とする
- ローカル設定ファイルを使う場合は Git 管理対象外にする
- Blender 側 UI には秘密情報そのものを表示しない
- 接続先、タイムアウト、ログレベルなどの運用設定は MCP サーバー側に寄せる
- Blender 側には最小限の接続設定のみ持たせる

## 5. 安全設計

- 実行コマンドは allowlist 型で管理する
- 引数スキーマを事前検証する
- 危険操作は `preview -> confirm -> execute` の 3 段階とする
- ローカルバインドのみを既定値にする

### 5.1 操作分類

- 自動実行可能操作
  - 接続確認
  - オブジェクト一覧取得
  - 単一プリミティブ生成
  - 単一オブジェクトの基本変形
- 承認必須操作
  - 単一オブジェクト削除
  - オブジェクト削除
  - モディファイア適用
  - 既存データ上書き
  - 複数オブジェクト一括変更
- 禁止操作
  - 任意 Python 実行
  - 自由形式 `bpy` 実行
  - 公開ネットワーク越し制御

### 5.2 承認フロー境界

- AI から返る提案は即時実行しない
- `executionMode=confirm_required` を受けた場合のみ、UI 上で承認待ちへ送る
- UI で承認されるまでは Blender 本体へ破壊的変更を適用しない
- 却下時は実行せず履歴と監査ログのみに残す
- 承認後実行が失敗した場合は再承認不要でエラー状態へ戻す
- Phase 1 では単一オブジェクト削除を承認必須操作として含める

### 5.2.1 承認結果の返却方針

- 現在の MVP では、承認待ちになった request は Blender UI が `requestId` と command 本体を保持する
- 承認後の実行結果は Blender UI の履歴と結果表示で確認できるようにする
- 最初の MCP tool 呼び出しは `confirm_required` を返した時点で完了扱いとする
- 承認後の最終結果を Codex 側へ再通知する完全フローは別 Issue で拡張する

### 5.3 引数検証ポリシー

- 数値配列の長さ、型、範囲を事前検証する
- 対象オブジェクト名未指定の変更操作は拒否する
- allowlist 外の `action` は即時拒否する
- 変形量や生成種別が安全閾値を超える場合は失敗または承認対象へ送る

## 6. 監査/ログ

- MCP サーバー側に操作要求ログを記録
- Blender 側に実行結果ログを記録
- エラー時は例外種別、対象操作、主要引数を残す

### 6.1 監査ログ最小項目

- `requestId`
- タイムスタンプ
- 呼び出し元ツール名
- `action`
- `executionMode`
- 承認要否
- 実行結果
- エラーコード
- 対象オブジェクト名
- 主要引数の要約

### 6.2 ログの扱い

- 秘密情報はログへ出力しない
- API キー、完全な認証情報、機微な環境値は除外する
- AI 応答全文は初期段階では必須保存対象にしない
- 問題調査に必要な最小限の要約情報を残す

## 7. 設計上の主なリスク

- Blender UI スレッドと通信処理の整合
- AI 応答の曖昧さによる不正操作
- バージョン差異による `bpy` API 挙動差
- 依存ライブラリが Blender 同梱 Python と衝突する可能性
- MVP 前倒しで UI 構造を広げることによる初期工数増

## 8. リスク緩和

- 初期は操作種別を絞る
- 自然言語を直接実行せず構造化コマンドへ変換する
- Blender 側の通信依存を最小限に抑える
- 外部依存が重い処理は MCP サーバー側へ寄せる
- UI は多モジュール化するが、各モジュールは最小責務に保つ
